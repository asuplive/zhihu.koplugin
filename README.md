# Zhihu Reader for KOReader v154

在 KOReader 中浏览知乎推荐流，支持二维码登录和整页翻页阅读。

## 功能

- 二维码扫码登录知乎账号（扫码确认后自动完成登录）
- 知乎风控（人机验证）检测与浏览器验证流程，修复安卓扫码"无反应"
- 查看个性化推荐流（需登录，每批 12 条，可 Load More 加载更多）
- 基于 ScrollHtmlWidget 的图文混排阅读器
- 全部图片都能加载，并自动压缩到屏幕宽度（低内存设备也不会卡死）
- 图片持久化缓存：下载一次后按文章保存在 `zhihu_article_images/<问题ID>/` 文件夹，下次打开同一篇直接显示，不再重复下载
- 字体大小调节（Small/Medium/Large/Extra Large）
- 导出 HTML（base64 内联图片，自动打开）
- 导出 EPUB（自动打开，无重复标题）

## 安装

将 `zhihu.koplugin` 文件夹复制到 KOReader 插件目录：

- **Kindle**：`koreader/plugins/`
- **Kobo**：`.adds/koreader/plugins/`
- **PocketBook**：`applications/koreader/plugins/`
- **Android**：KOReader 数据目录下的 `plugins/`

重启 KOReader，在主菜单 → 工具 → Zhihu Reader 中打开。

## 使用

### 登录
1. 菜单中选择 Login with QR Code
2. 手机知乎 App 扫描二维码
3. 手机上确认登录，插件自动轮询并完成登录

### 安卓风控（人机验证）
部分网络环境（常见于手机流量、运营商 NAT 出口 IP）会被知乎风控拦截：扫码状态接口返回
HTTP 403 / 错误码 40352，并要求跳转 `zhihu.com/account/unhuman` 做滑块人机验证。旧版本会把
这种响应当作"等待中"无限轮询，表现为**扫码后没反应**。

v128 起的处理流程：
1. 检测到风控后自动停止轮询，弹出「Zhihu Verification Needed」菜单
2. 选择 **Open Verification in Browser**：调起系统浏览器打开验证页（安卓支持），完成滑块验证
   - 不支持调起浏览器的设备可选择 **Show Verification URL** 手动打开该链接
3. 验证完成后回到 KOReader，选择 **I Have Verified - Continue Login** 继续轮询，登录自动完成
4. 若仍被拦截，可选 **Restart Login (Fresh Cookies)**：丢弃被标记的 `d_c0` 设备标识、
   重新获取 cookie 并生成新二维码

> 说明：验证页是 JavaScript 滑块验证码，KOReader 的 HTML 渲染器无法运行 JS，因此无法在
> 插件内直接显示验证界面，需要借助系统/外部浏览器完成。验证会话与本客户端的 cookie 绑定，
> 在同一网络下于浏览器完成验证后，KOReader 的后续请求即可恢复。Kindle 等未被风控的设备
> 不受影响。

### 浏览推荐
登录后菜单出现 Recommended Feed，点击加载内容列表，每批显示 12 条。列表底部有 >>> Load More >>> 按钮按游标加载下一批。

### 阅读文章
点击列表项进入 ArticleViewer：
- 左右滑动/点击翻页
- 上下滑动关闭
- 按返回键退出

开启 Show Images 时，**文章里的每一张图片都会加载**：
- 下载进度显示在**屏幕最下方一条细状态栏**（如 `Images: 3/12`），不弹窗、不遮挡正文
- 状态栏**只在翻页时刷新**，不会每下载一张图就闪一次屏（e-ink 友好）
- **下载时可以正常翻页阅读**，不再被阻塞；**每张图片一下载完就立刻出现在页面上**（保持当前页码原地刷新），不必等全部图片下载完
- 宽度超过屏幕的图会自动压缩为屏幕宽度的 PNG（观感无差别，解码内存从几十 MB 降到约 2MB）
- **二次打开直接读缓存**：图片按文章保存在 KOReader 数据目录下的 `zhihu_article_images/<问题ID>/` 文件夹（如 `img_001.png`），首次打开时已下载并压缩好的图，下次打开**立即显示、不再走网络**；未缓存的图才会在后台下载并写入该文件夹

### 导出
阅读时打开菜单选择 Export HTML 或 Export EPUB，导出后自动在 KOReader 中打开。

## 文件结构

```
zhihu.koplugin/
  _meta.lua           -- 插件元数据
  main.lua            -- 主逻辑（菜单、UI、登录、导出）
  article_viewer.lua  -- 文章阅读器（ScrollHtmlWidget）
  epub_builder.lua    -- EPUB 生成器
  zhihu_client.lua    -- HTTP 客户端与 HTML 解析
  README.md           -- 本文件
```

## 更新日志

### v154
- **新增「刷新模式 (Refresh Mode)」设置**，共四种，默认 **Regal 刷新**：
  - 全刷 (Full Refresh)：每次重绘都做完整刷新，最干净但最慢（Kindle 上约 1 秒）
  - 局刷 (Partial Refresh)：每次都是局部刷新，最快，但连续翻页会逐渐留下残影
  - 局部刷新 6 次后全刷 (Partial x 6, then Full)：翻页连刷 6 次局部后自动插入一次全刷清残影；图片落地那一次也按全刷处理
  - Regal 刷新 (Regal, Default)：请求 `flashpartial` 刷新类型，在支持 REAGL/Regal 的屏幕上由驱动换成 Regal 波形（高画质、无黑闪）；不支持 REAGL 的机型退化为一次带闪的局部刷新，仍比全刷省时、且不留残影
- **图片不再「下一张刷一次」**：原先每下载完一张图就整篇 `setContent` 重排并刷新一次屏幕。现在后台照旧逐张下载、但**不碰屏幕**；等这一批图片全部落盘后，**在下次翻页时**连同翻页本身一次性刷出整批图片——一次翻页、一次刷新
- 兜底：若这一批图片下载完读者一直不翻页，则在 8 秒后自动补刷一次（避免停在末页时图片永远不出现）；下载失败仍按 `[图片]` 占位
- 三种设置都作用于翻页与图片落地这一次刷新，切换后重新打开文章即生效

### v150
- **彻底修复"图片偏右"**：v149 把图片包进 `<div class="img-block">` 并设 `text-align: center`，但样式表里 `img { display: block }` 让图片是**块级盒子**——块级盒子不理会父级的 `text-align`，只会贴着自己容器的左边缘。于是图片左侧留着页面边距、右侧一直顶到（甚至溢出）页边距，看过去就是"整体偏右"。
  - 图片改为行内（`img { display: inline }`，并在 `<img>` 上同时写 `style="display:inline"`），父级的 `text-align: center` 才真正对图片生效。
  - 图片容器补 `width: 100%`，保证居中参照的是整栏宽度而不是被内容撑窄的盒子。
- **图片宽度改为按文字栏宽度计算**：原来按屏幕原始宽度（`屏宽 - 14`）算目标宽度，比 crengine 实际文字栏更宽，图片横向溢出到右侧页边距之外。现在按 `屏宽 - 2 × max(屏宽 × 7%, scaleBySize(10))` 取宽，并且若能从 crengine 读到真实栏宽（`getPageWidth()`）就取两者较小值，图片不会再溢出栏目。同步改了 `zhihu_client.getRenderImgWidth()`，首屏图片尺寸一致。
- **上下留白加大**：`div.img-block` 的 `margin` 由 `8px 0` 改为 `0.8em 0`（随字号缩放），图片与上下文字之间的空隙更明显。

### v149
- **正文图片居中**：每张正文图片用 `<div class="img-block">` 包起来，加 `text-align: center; text-indent: 0`，用意是取消段落首行缩进、并把图片居中。单独占页模式下用 `class="img-block page-img"`。
- 实际效果受 `img { display: block }` 影响，居中未生效（由 v150 修正）。

### v148
- **图片上下留白**：`img.full-img` 原来没有任何 margin，图片紧贴上下文字，一页里显得又挤又薄。现在加 `margin: 10px 0`。
- **新增设置「图片排版」**：
  - `图片与上下文字留白（默认）`：图片仍在正文流里，只是加了上下留白；
  - `图片单独占一页（另起页显示）`：每张正文图片用 `<div class="page-img">` 包起来，带 `page-break-before/after: always`，让图**另起一页、独占一页**，不再和正文抢同一页的剩余高度。改后重新打开文章生效。
  - 注：能否真正分页取决于 crengine 对 `page-break` 的支持；若不认，退化为"加留白"，不会影响正常阅读。

### v147
- **修复"个别图仍然很小"**：根因在尺寸来源，不在缩放代码。知乎给不少真实照片的 `data-rawwidth` 标成 <=160（或干脆没有宽度信息），`cleanHtmlForRender` 据此把图判成 `tiny-img` 并且**不写 width 属性**，crengine 只能按位图原始像素排版 —— 一张 160px 宽的图在 1072px 屏上就只有 15% 屏宽，正是截图里左下角那张。
  - 现在宽度判断**改为读落地后的位图**：`article_viewer.lua` 新增 `imagePixelWidth()`，只解析 PNG IHDR / GIF / JPEG SOF 头（不解码、不占内存），按真实像素宽决定排版宽度
  - 真实照片（宽 > 96px）：宽度 = `min(文本栏宽, max(2×原图宽, 55% 栏宽))`，即小图至少放大到约半屏宽，大图仍撑满栏宽，低清图不会被无脑拉爆
  - 真表情/图标（宽 <= 96px）：保持原尺寸、`tiny-img` 内联，不会被放大成马赛克块
- **修复"第二次打开文章，图又变小了"**：`main.lua` 命中本地缓存时原来返回 `<img src="缓存文件名" alt=""/>`，把 `width`/`class` 全丢了，缓存图只能按原始像素显示；现在缓存路径原样保留这两项属性。这也是同一张图"首次打开正常、再进来变小"的原因。
- 该修复对**已缓存的旧图同样生效**（尺寸在渲染时按磁盘上的文件重新计算，无需删缓存重下）。

### v146
- **修复"当前页的图下载了却不显示、最后一起冒出来"**：根因不在节流，而在刷新时重排用的 HTML。此前每次刷新都从"远程图 URL 版本"的 HTML 重建页面，而屏幕上画的是"占位符版本"——一次刷新会把页面上所有 `[图片N]` 占位同时替换成 `<img>`，占位高度与图片高度不同，整篇排版瞬间塌陷/位移，读者被甩到别处，可视区里只剩"最后一下全变"。现在改为：
  - 以屏幕上的占位版 HTML 为底稿，**只把已经下好盘的那一张图放进它自己的占位槽位**，其余占位原地不动，重排后位移最小，当前页的图一下好就出现在当前页
  - 中间过程用 `partial` 局部刷新（`full` 全刷在 Kindle 上要近一秒，连续多次会被驱动合并成一次，正好表现为"最后一起刷"），收尾仍用 `full` 清残影
  - 节流从 0.4s 缩到 0.1s；翻页中推迟的重排在翻页结束后立即补上
  - 内容未变化时完全不重排、不刷屏，翻页不受干扰
- **段落首行缩进可选**：设置里新增「段落首行缩进」——`不缩进（贴最左）` 或 `缩进两个汉字`（默认）。原来固定 `0.5em`（半个字）不好看的问题解决；导出 HTML 的样式同步跟随该设置。改设置后重新打开文章生效。

### v145
- **修复"图片下载了但页面不刷新"**：v143/v144 把刷新目标写成了 `UIManager:setDirty(self.html_widget, "full")`。`ScrollHtmlWidget` 自身没有注册区域（dimen），这一句会被静默丢弃 —— 结果就是图片文件已经写进缓存目录、底部进度也在走，屏幕却一动不动。现在改为对阅读器本体 `UIManager:setDirty(self, "full")`（与原 v132 之前的整篇刷新一致），并额外把内部 `dialog` 一并标脏作为双保险。

### v144
- **图片严格从文章开头往后出现**：v143 里图片虽然逐张显示，但受"下载/重编码耗时 + 0.4 秒节流合并"影响，偶尔会看到**靠后的图先冒出来**。现在加了一条顺序水位线：
  - 下载队列按图片在文章中的位置排序（`img_index` 升序），串行处理
  - 每张图处理完（成功或失败）才放行下一张进入"可显示"区间，**第 5 张绝不会在第 2 张之前出现在页面上**
  - 已缓存的图、下载失败的图不会阻塞队列（失败直接跳过，位图显示为 `[图片]` 占位）
  - 全部结束后再做一次收尾刷新，统一把失败图落成占位符

### v143
- **图片改为逐张就地显示**：此前是"全部图片下载完 → 一次性 `setContent` 刷新整篇"，图片多的文章要盯着空白等很久。现在**每张图片下载完就在页面上出现**
  - 下载成功即触发一次原地刷新，只把已下载图片的 `src` 换成本地文件，未完成的图保持原样
  - 刷新**保持当前页码**（并夹紧越界页码），不会把读者甩到别的页
  - 0.4 秒节流合并：连续快速下载的图片合并为一次重排，避免反复重排拖慢慢速 e-ink 设备
  - 读者正在翻页（`_navigating`）时最多推迟两次，不会长时间打断阅读
  - 全部结束再做最后一次收尾刷新，把下载失败的图统一回退为 `[图片]` 占位符
- 下载间隔由 0.3s 缩短到 0.2s，图片出现更连贯

### v132
- **修复图片缓存未生效**：v131 实际丢失了上一版的缓存机制，每次打开文章都会重新下载——表现为"每次都走网络、底部进度条重新跑一遍"。两个根因：
  1. main.lua 只认 `img_%03d.png` 缓存名，但宽度没超过屏幕的图（知乎配图多为 690px，Kindle 屏宽约 758px）不会被压缩，仍是原始扩展名（如 `img_001.jpg`），于是**永远不被识别为缓存**
  2. article_viewer.lua 的 `ensureImage` 在 URL 本身以 `.png` 结尾时，`orig_path == png_path`，`os.remove(orig_path)` 把刚写好的缓存图删掉，导致**每次都重新下载**
- **修复后的缓存行为**：
  - 下载与压缩结果**持久保存在 `zhihu_article_images/<问题ID>/` 文件夹**（`img_NNN.png` 优先，原扩展名文件 `img_NNN.<ext>` 作为小图/无法重编码图的缓存）
  - 打开文章时 main.lua 先查这两个缓存名，**命中即直接渲染、不走网络**
  - 超过 8MB 的缓存文件会被视为异常大图，自动重新下载并压缩（防止超大全分辨率图占满内存）
  - 卸载/清缓存只需删除 `zhihu_article_images/` 目录即可
- 版本号、About 信息与文档同步更新为 v132

### v131
- **下载进度改为底部状态栏**：移除居中的 `InfoMessage` 弹窗（会遮挡正文），改为屏幕最下方预留一条
  细状态栏（22px），显示 `Images: 3/12`，**不覆盖任何文字**

- **下载期间可以正常阅读**：取消下载时的输入阻塞（滑动/tap/关闭都不再被吞掉），可以边读边等；
  背景下载完成才做一次原地刷新
- 布局改动用 `pcall` 保护：若底部状态栏构建失败，自动回退为整屏正文（不影响阅读）
- 版本号、About 信息与文档同步更新为 v131

### v129
- **修复 Kindle 打开图片多的文章直接卡死**。原因有三，叠加生效：
  1. 每张图片的下载都是同步 HTTP 请求，会阻塞 UI 线程——Kindle 的 CPU/WiFi 都慢，几十张图
     就是连续数分钟无响应；
  2. 下载期间 tap/swipe/翻页全部被拦截，屏幕上又没有任何进度提示，看起来与死机无异；
  3. 下载结束后的 `setContent` 一次性把所有图片同时解码渲染，慢速 e-ink CPU 上 burst 解码
     长时间占死，大图还可能耗尽内存造成真死机
- **图片数量上限**：每篇文章最多加载 10 张（`MAX_ARTICLE_IMAGES`），其余保持 [图片N] 占位符，
  仍可通过 View Images 菜单逐张查看原图
- **图片大小上限**：单张超过 3MB（`MAX_IMAGE_BYTES`）的图片直接跳过（缓存中的超限文件也会
  被清理），避免大图解码拖垮低内存设备
- **下载进度提示**：后台下载时显示「Downloading images (i/N)...」，关闭阅读器时自动清除，
  不再"无声卡住"
- **修复刷新后失败图片变空白**：后台刷新时，未能加载（下载失败/被跳过/超限）的图片现在回落
  为 [图片] 占位符，而不是残留一个加载不出来的远程地址
- **导出保护**：Export EPUB 下载图片时也显示进度（此前完全静默）；Export HTML / Export EPUB

### v128
