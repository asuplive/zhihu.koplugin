# Zhihu Reader for KOReader v160

在 KOReader 中浏览知乎推荐流，支持二维码登录和整页翻页阅读。

## 功能

- 二维码扫码登录知乎账号（扫码确认后自动完成登录）
- 知乎风控（人机验证）检测与浏览器验证流程，修复安卓扫码"无反应"
- 查看个性化推荐流（需登录，每批条数可在设置中选 6/12/18/24/30/36，默认 12，可 Load More 加载更多）
- 基于 ScrollHtmlWidget 的图文混排阅读器
- 全部图片都能加载，并自动压缩到屏幕宽度（低内存设备也不会卡死）
- 图片持久化缓存：下载一次后按文章保存在 `zhihu_article_images/<问题ID>/` 文件夹，下次打开同一篇直接显示，不再重复下载
- 字体大小调节（Small/Medium/Large/Extra Large）
- 字体族设置（Font Family）：推荐流列表与文章正文都按所选字体显示，自动匹配设备上的真实字体文件；只含西文字形的族（如 Noto Serif）会标注「仅西文」并自动换用同族的中文字体；菜单内提供「设备上的中文字体」与「字体诊断」，可查看正文实际使用的字体与 CSS
- 导出 HTML（base64 内联图片，自动打开）
- 导出 EPUB（自动打开，无重复标题）
- 菜单按用途分组：推荐流 / 阅读设置 / 排版与刷新 / 缓存与导出 / 设置，打开「设置」就能看到推荐流条数、当前设置一览与关于

## 安装

将 `zhihu.koplugin` 文件夹复制到 KOReader 插件目录：

- **Kindle**：`koreader/plugins/`
- **Kobo**：`.adds/koreader/plugins/`
- **PocketBook**：`applications/koreader/plugins/`
- **Android**：KOReader 数据目录下的 `plugins/`

重启 KOReader，在主菜单 → 工具 → Zhihu Reader 中打开。

## 使用

### 登录
1. 菜单中选择 Login with QR Code
2. 手机知乎 App 扫描二维码
3. 手机上确认登录，插件自动轮询并完成登录

### 安卓风控（人机验证）
部分网络环境（常见于手机流量、运营商 NAT 出口 IP）会被知乎风控拦截：扫码状态接口返回
HTTP 403 / 错误码 40352，并要求跳转 `zhihu.com/account/unhuman` 做滑块人机验证。旧版本会把
这种响应当作"等待中"无限轮询，表现为**扫码后没反应**。

v128 起的处理流程：
1. 检测到风控后自动停止轮询，弹出「Zhihu Verification Needed」菜单
2. 选择 **Open Verification in Browser**：调起系统浏览器打开验证页（安卓支持），完成滑块验证
   - 不支持调起浏览器的设备可选择 **Show Verification URL** 手动打开该链接
3. 验证完成后回到 KOReader，选择 **I Have Verified - Continue Login** 继续轮询，登录自动完成
4. 若仍被拦截，可选 **Restart Login (Fresh Cookies)**：丢弃被标记的 `d_c0` 设备标识、
   重新获取 cookie 并生成新二维码

> 说明：验证页是 JavaScript 滑块验证码，KOReader 的 HTML 渲染器无法运行 JS，因此无法在
> 插件内直接显示验证界面，需要借助系统/外部浏览器完成。验证会话与本客户端的 cookie 绑定，
> 在同一网络下于浏览器完成验证后，KOReader 的后续请求即可恢复。Kindle 等未被风控的设备
> 不受影响。

### 浏览推荐
登录后菜单出现 Recommended Feed，点击加载内容列表，每批条数由设置里的「推荐流条数 (Feed Batch Size)」决定（6/12/18/24/30/36，默认 12）。列表底部有 >>> Load More >>> 按钮按游标加载下一批。

### 阅读文章
点击列表项进入 ArticleViewer：
- 左右滑动/点击翻页
- 上下滑动关闭
- 按返回键退出

开启 Show Images 时，**文章里的每一张图片都会加载**：
- 下载进度显示在**屏幕最下方一条细状态栏**（如 `Images: 3/12`），不弹窗、不遮挡正文
- 状态栏**只在翻页时刷新**，不会每下载一张图就闪一次屏（e-ink 友好）
- **下载时可以正常翻页阅读**，不再被阻塞；**每张图片一下载完就立刻出现在页面上**（保持当前页码原地刷新），不必等全部图片下载完
- 宽度超过屏幕的图会自动压缩为屏幕宽度的 PNG（观感无差别，解码内存从几十 MB 降到约 2MB）
- **二次打开直接读缓存**：图片按文章保存在 KOReader 数据目录下的 `zhihu_article_images/<问题ID>/` 文件夹（如 `img_001.png`），首次打开时已下载并压缩好的图，下次打开**立即显示、不再走网络**；未缓存的图才会在后台下载并写入该文件夹

### 导出
阅读时打开菜单选择 Export HTML 或 Export EPUB，导出后自动在 KOReader 中打开。

## 文件结构

```
zhihu.koplugin/
  _meta.lua           -- 插件元数据
  main.lua            -- 主逻辑（菜单、UI、登录、导出）
  article_viewer.lua  -- 文章阅读器（ScrollHtmlWidget）
  epub_builder.lua    -- EPUB 生成器
  zhihu_client.lua    -- HTTP 客户端与 HTML 解析
  README.md           -- 本文件
```

### v158 (修复 v157 崩溃)
- **修复「点字体设置直接崩溃、Article View 打不开」**：v157 从三处（正文 CSS 的字体别名、字体菜单的「设备上的中文字体」、字体诊断页）调用了 `cjkFontFaces()`，但这个函数从未定义。点字体菜单、或打开文章（同样要构建正文 CSS）时就会抛 `attempt to call a nil value`，KOReader 直接崩溃；「文本查看」不走自定义 CSS，所以还能正常读。现已补上该函数的定义
- **候选顺序修正**：v157 的中文字体候选会把用户所选字族挤出 `font-family`，现在先放所选字族解析出的字体文件（2 个），再补 1 个设备中文字体兜底
- **字体名改用真实族名**：`fontlist` 同时报告 PostScript 名（`NotoSerifCJKsc-Regular`）与真实族名（`Noto Serif CJK SC`），此前可能选中 PostScript 名或纯文件名，菜单与 CSS 里看着像乱码；现在按「含空格的真实族名 > 无连字符的族名 > 其他」打分择优
- **字体元数据缺失时的中文字体识别**：部分 KOReader 构建的 `fontlist.fontinfo` 不带 script/language 覆盖（此前这类字体被归为「未知」而不进中文列表，如 `wqy-microhei`）。现在按名字兜底识别（`cjk` / `fallback` / `hei` / `wqy` / `yahei` / `simsun` 等），仍然「看不出来」才保留为未知
- **所选族名命中中文字体文件时不再走错名字**：若 `Noto Serif` 只匹配到 `NotoSerifCJK-Regular.ttc`，CSS 改用该文件的真实族名 `Noto Serif CJK SC`，避免 MuPDF 因 `Noto Serif` 命中旁边的纯西文 `NotoSerif-Regular.ttf` 而对汉字回退内置字体
- **字体库读取全程容错**：`fontlist` 缺失、`getFontList()` 抛错、`fontinfo` 不是表时都不再影响菜单与正文，最多是没有自定义字体
- 生效方式：替换插件目录后重新打开文章即可（无需重启 KOReader）

### v157
- **修复「字体设置了但汉字没变」的根因：所选字族不含汉字字形**。诊断截图显示，设置为 `Noto Serif` 时 36 个候选全部命中，但 `Noto Serif` 是纯西文字体，一个汉字都没有；MuPDF 排到汉字时只能回退到内置 CJK 字体，于是整页看起来和没设置一样。之前几版一直在解决"名字匹配不上"，这一次解决"匹配上了但字不全"
- **候选按汉字覆盖过滤与排序**：读取 `fontlist` 里 HarfBuzz 报告的 script/language 覆盖，给每个字体文件打「含汉字 / 仅西文 / 未知」标记；CSS 里含汉字的文件排最前，纯西文字体不再抢占第一位
- **自动换用同族中文字体**：选了 `Noto Serif` 这类纯西文族时，自动改用同族的中文字体（如 `Noto Serif CJK SC`），并在提示里说明「「Noto Serif」不含汉字字形，正文改用 Noto Serif CJK SC」；拉丁字母仍保留用户选择
- **`font-family` 大幅缩短**：原来把 36 个候选 × 3 种写法全写进一条规则（上百个 token），中文候选被挤到很后面；现在只保留含汉字的前几个候选，规则从上百 token 降到十几个
- **字体菜单分组与标注**：中文族排前面，纯西文族标注「仅西文」；新增「设备上的中文字体（N）」子菜单，直接列出本机真实存在的中文字体，不用再靠猜名字
- **诊断页新增「含汉字」判定**：显示所选族名是否含汉字、正文实际使用哪个字体、是否发生自动替换、设备含汉字的字体文件数，以及每个候选的「含中文 / 仅西文」标签——这样就能区分"选错字族"与"引擎不吃自定义字体"

### v156
- **去掉正文 CSS 里的 `@font-face`**：文章正文由 MuPDF 排版引擎渲染，它不解析 `@font-face`，v155 注入的那条规则从未真正绑定字体，只是让样式表多了一段引擎要跳过的声明。现已移除
- **`font-family` 首选「磁盘上的字体文件名（含扩展名）」**：MuPDF 是按字体文件名去查找字体的，v155 只把「去扩展名的文件名」交给引擎，引擎再补 `.ttf` 就永远找不到 `.ttc` / `.otf` 字体（例如 `NotoSansCJK-Regular.ttc`），这是「正文仍是默认字体」最可能的原因。现在顺序为：带扩展名文件名 → 去扩展名文件名 → 字体内部族名 → 所选族名及别名 → 内置中文字体栈
- **新增「字体诊断 (Font diagnostics)」菜单项**：一页显示当前设置值、排版引擎版本、设备字体文件数、匹配到的字体文件与绝对路径、以及正文真正使用的 `font-family` 字符串。以后正文没变时，先看这一页就知道是"字体名没匹配上"还是"引擎不吃自定义字体"
- **提示文案不再含糊**：设置字体后的提示仍会报出匹配到的文件，但明确提示「若正文仍是默认字体，请打开字体诊断」
- 生效方式：替换插件后重新打开文章即生效（无需重启 KOReader）

### v155
- **修复「设置了字体但没起作用」**。原来字体设置只被写进文章正文的 CSS，而推荐流列表是 KOReader 原生 Menu，用的一直是菜单默认字体；文章正文的字体名也常和设备上真实字体文件名对不上（族名 `Noto Serif CJK SC` ≠ 文件名 `NotoSansCJK-Regular.ttc`），渲染引擎找不到就直接回退默认字体，看起来就是设置无效
- **推荐流列表套用所选字体**：用 `Font:getFace` 把所选族名解析成设备上真实可加载的字体文件，再作为 Menu 的字体，列表内容与设置一致
- **正文增强解析**：CSS `font-family` 现在依次尝试「所选族名 → 去掉空格的形式 → 匹配到的族名/文件名别名 → 内置中文字体栈」，并追加一条本地 `@font-face` 规则（`src:url("file:///...")`），直接把具体字体文件交给布局引擎，绕开名称查不到的问题
- **族名/文件名双向匹配**：从字体库读取每个字体文件内 FreeType/HarfBuzz 报告的真实族名，族名与文件名两个方向都做归一化匹配（忽略大小写、空格、连字符、扩展名），常规体优先于 Bold/Italic
- **设置后立刻看得出是否匹配上**：选定字体会提示「已匹配字体文件：xxx（族名）」，若设备上找不到同名文件则明确提示「将按字体名交给渲染引擎」，不再只是干巴巴一句"已保存"
- 生效方式：设置后重新打开推荐流 / 文章即生效（无需重启 KOReader）

### v154
- **新增「刷新模式 (Refresh Mode)」设置**，共四种，默认 **Regal 刷新**：
  - 全刷 (Full Refresh)：每次重绘都做完整刷新，最干净但最慢（Kindle 上约 1 秒）
  - 局刷 (Partial Refresh)：每次都是局部刷新，最快，但连续翻页会逐渐留下残影
  - 局部刷新 6 次后全刷 (Partial x 6, then Full)：翻页连刷 6 次局部后自动插入一次全刷清残影；图片落地那一次也按全刷处理
  - Regal 刷新 (Regal, Default)：请求 `flashpartial` 刷新类型，在支持 REAGL/Regal 的屏幕上由驱动换成 Regal 波形（高画质、无黑闪）；不支持 REAGL 的机型退化为一次带闪的局部刷新，仍比全刷省时、且不留残影
- **图片不再「下一张刷一次」**：原先每下载完一张图就整篇 `setContent` 重排并刷新一次屏幕。现在后台照旧逐张下载、但**不碰屏幕**；等这一批图片全部落盘后，**在下次翻页时**连同翻页本身一次性刷出整批图片——一次翻页、一次刷新
- 兜底：若这一批图片下载完读者一直不翻页，则在 8 秒后自动补刷一次（避免停在末页时图片永远不出现）；下载失败仍按 `[图片]` 占位
- 三种设置都作用于翻页与图片落地这一次刷新，切换后重新打开文章即生效

### v150
- **彻底修复"图片偏右"**：v149 把图片包进 `<div class="img-block">` 并设 `text-align: center`，但样式表里 `img { display: block }` 让图片是**块级盒子**——块级盒子不理会父级的 `text-align`，只会贴着自己容器的左边缘。于是图片左侧留着页面边距、右侧一直顶到（甚至溢出）页边距，看过去就是"整体偏右"。
  - 图片改为行内（`img { display: inline }`，并在 `<img>` 上同时写 `style="display:inline"`），父级的 `text-align: center` 才真正对图片生效。
  - 图片容器补 `width: 100%`，保证居中参照的是整栏宽度而不是被内容撑窄的盒子。
- **图片宽度改为按文字栏宽度计算**：原来按屏幕原始宽度（`屏宽 - 14`）算目标宽度，比 crengine 实际文字栏更宽，图片横向溢出到右侧页边距之外。现在按 `屏宽 - 2 × max(屏宽 × 7%, scaleBySize(10))` 取宽，并且若能从 crengine 读到真实栏宽（`getPageWidth()`）就取两者较小值，图片不会再溢出栏目。同步改了 `zhihu_client.getRenderImgWidth()`，首屏图片尺寸一致。
